# مشخصات زبان Raz و کامپایلر

**وضعیت:** پیش‌نویس ۰.۲
**نسخه‌ی هدف این سند:** `raz-1.0` (نخستین نسلی که با کامپایلر نسل قبل ساخته می‌شود)

## برچسب‌های این سند

- **[قطعی]**: تصمیمی است که کاربر گرفته و در سند ثبت شده است.
- **[پیشنهاد]**: پیشنهاد نویسنده‌ی سند است و هنوز تأیید نشده.
- **[باز]**: موضوعی است که باید قبل از نوشتن کد تصمیم‌گیری شود. فهرست کامل در بخش ۲۳ آمده است.

## ۰. تغییرات نسبت به پیش‌نویس ۰.۱

| موضوع | پیش‌نویس ۰.۱ | پیش‌نویس ۰.۲ | وضعیت |
|---|---|---|---|
| متغیر تغییرپذیر | `let` و `var` | فقط `let` (تغییرپذیر)؛ `const` برای تغییرناپذیر | [قطعی] |
| هدف امنیت حافظه | نبود | Raz زبانی **memory safe** است؛ اشاره‌گر در کد امن وجود ندارد | [قطعی] |
| اشاره‌گر | مجاز در کل زبان | فقط در بلوک `unsafe` و هدرهای native | [قطعی] |

| `try` / `catch` / `throw` | نبود | پیشنهاد می‌شود ولی با احتیاط؛ از نسل ۷ به بعد، اختیاری و با فلگ target | [پیشنهاد] |
| `main` | نبود | همچنان نداریم؛ برای `argv` از متغیرهای global کامپایلر استفاده می‌شود | [قطعی] |

| فرمول نسل‌ها | توضیح کلی | فرمول دقیق، شرط نقطه‌ی ثابت، و مثال گام‌به‌گام برای توسعه‌دهندگان | [قطعی] |

## ۱. اهداف

1. **امنیت حافظه (memory safety)**: زبان و کامپایلر طوری طراحی می‌شوند که برنامه‌ی کاربر بدون اشاره‌گر، بدون دسترسی آزاد به حافظه و بدون نشت حافظه‌ی دستی باشد. تا جای ممکن، مدیریت حافظه **خودکار** توسط زبان و کامپایلر انجام می‌شود. [قطعی]
2. **خودکارسازی**: هر کاری که کامپایلر یا زبان بتواند به‌صورت خودکار انجام دهد (مدیریت منابع، آزادسازی، بررسی تایپ) نباید بر عهده‌ی برنامه‌نویس باشد. [قطعی]
3. **زبان نزدیک به سخت‌افزار و ساده**: تایپ‌ها، عبارات و ساختارها مستقیم به معادل C/C++ نگاشت می‌شوند تا کد تولیدشده قابل پیش‌بینی و سریع باشد. [قطعی]
4. **کامپایل از طریق C++17 و GNU**: خروجی کامپایلر کد C++17 است و با `g++`/`gcc` ساخته می‌شود تا از بهینه‌سازی‌های کامپایلر و سخت‌افزار بهره ببرد. [قطعی]
5. **بدون overhead**: برنامه‌ی ساخته‌شده هیچ runtime اضافه، GC، یا سربار پنهان ندارد. [قطعی]
6. **زبان اسکریپتی در سطح فایل**: کد خط‌به‌خط اجرا می‌شود. فایل اصلی نقطه‌ی شروع است و کاربر تابع `main` نمی‌نویسد. [قطعی]
7. **خودمیزبانی نسل‌به‌نسل**: کامپایلر در هر نسل، کامپایلر نسل بعد را کامپایل می‌کند و قابلیت‌ها به‌تدریج اضافه می‌شوند. [قطعی]
8. **کامپایلر حداقلی**: کامپایلر فقط «زبان» را می‌شناسد. توابع کتابخانه‌ای مانند `echo` در کامپایلر تعریف نمی‌شوند و از هدرهای خارجی می‌آیند. [قطعی]

## ۲. غیرهدف‌ها

- کلاس، وراثت، متد، و `private` / `protected` / `public`. [قطعی]
- کلیدواژه‌های `export` و `extern`. [قطعی]
- `new` و `null`. (`nullptr` فقط در بلوک `unsafe` و هدرهای native؛ بخش ۴) [قطعی]
- تایپ‌های پیچیده و generic تعریف‌شده توسط کاربر. [قطعی]
- `Ref<T>` و `->` به‌عنوان نوع تایپ. [قطعی]
- `var`. [قطعی]
- عملگر `===`. [پیشنهاد]
- تابع `main` که کاربر بنویسد. [قطعی]
- استثنای نامدیریت‌شده: در کد امن، هر خطای اجرایی باید مدیریت شود یا به کد خروج تبدیل شود (بخش ۴.۶). [پیشنهاد]

## ۳. اصول

1. **هیچ چیز اضافه‌ای وجود ندارد**: هر کلیدواژه، عملگر، تایپ و قابلیت باید در این سند تعریف شده باشد. [قطعی]
2. **امن به‌صورت پیش‌فرض**: هر قابلیتی که بتواند باعث دسترسی نامعتبر به حافظه شود، فقط در بلوک `unsafe` یا هدر native مجاز است. [قطعی]
3. **همه‌چیز public است**: هیچ کلیدواژه‌ی دسترسی وجود ندارد. [قطعی]
4. **تایپ همیشه مشخص است**: هر متغیر، پارامتر و مقدار بازگشتی تایپ صریح دارد. [قطعی]
5. **مقدار اولیه‌ی اجباری**: هر `let` باید مقدار اولیه داشته باشد. متغیر بدون مقدار اولیه خطای کامپایل است. [پیشنهاد]
6. **`;` اجباری است**. [قطعی]
7. **معنای عملگرها همان C است**. [پیشنهاد]
8. **شرط کامپایل نباید منطق برنامه را محدود کند**: `include` و `use` در هر جایی که دستور مجاز است قرار می‌گیرند. [قطعی]

## ۴. حافظه و ایمنی

این بخش یکی از اهداف اصلی زبان است. هدف این است که برنامه‌نویس **هرگز** مجبور نباشد حافظه را دستی مدیریت کند، مگر در بلوک `unsafe` یا هنگام استفاده از هدرهای native.

### ۴.۱ اشاره‌گر [قطعی]

- اشاره‌گر (`T*`، `&x`، `*p`، `->`) در کد امن وجود ندارد.
- اشاره‌گر فقط در دو جا قابل استفاده است:
  1. داخل بلوک `unsafe { ... }`.
  2. در هدرهای native (که کاربر آن‌ها را با `use "..."` وارد می‌کند).
- این یعنی زبان **امکان** استفاده از اشاره‌گر را دارد، ولی هیچ قابلیت زبان به آن نیاز ندارد.

```raz
unsafe {
    let p: i64* = nullptr;   // فقط مجاز داخل unsafe
}
```

### ۴.۲ `unsafe` [پیشنهاد]

- `unsafe { ... }` یک بلوک است که کامپایلر در آن بررسی‌های ایمنی اشاره‌گر را غیرفعال می‌کند.
- مسئولیت صحت حافظه در این بلوک با برنامه‌نویس است.
- کامپایلر باید بتواند `unsafe` ها را در گزارش نهایی بشمارد تا دیده شوند.
- `unsafe` در نسل ۱ تعریف می‌شود تا کامپایلر بتواند از `char*` استفاده کند (بخش ۴.۵).

### ۴.۳ مدیریت خودکار حافظه [پیشنهاد]

- مقادیر (`i64`، `struct`، `string`) **مالک حافظه‌ی خود هستند**. کامپایلر هنگام خروج از scope، حافظه‌ی آن‌ها را به‌صورت خودکار آزاد می‌کند.
- در C++ این با **RAII** (مثل `std::string` و `std::unique_ptr`) پیاده‌سازی می‌شود.
- در کد تولیدشده‌ی کامپایلر، برای حافظه‌ی پویا از `std::make_unique` و `auto` استفاده می‌شود. این موضوع در بخش نگاشت C++ (بخش ۱۸) آمده است.
- برنامه‌نویس `free`، `delete` یا `malloc` نمی‌نویسد.
- `new` وجود ندارد. تخصیص حافظه‌ی پویا در نسل‌های بعد از طریق یک نوع امن (مثل `Box<T>` که مالک یک مقدار روی heap است) اضافه می‌شود. [باز]

### ۴.۴ کپی و انتقال [پیشنهاد]

- `struct` به‌صورت مقداری کپی می‌شود، مانند C.
- انتقال مالکیت (move) برای مقادیر بزرگ در نسل‌های بعد اضافه می‌شود. تا آن زمان کپی پیش‌فرض است.
- هیچ ارجاع (reference) در کد امن وجود ندارد. تابع پارامترها را کپی می‌گیرد یا مقدار بازمی‌گرداند.

### ۴.۵ `string` و `char*` [قطعی]

| نوع | کجا | وضعیت |
|---|---|---|
| `string` | کد امن، از نسل ۱ | مالک حافظه‌ی خود است؛ نگاشت به `std::string`. **نوع پیشنهادی برای متن**. |
| `char*` | `unsafe` و هدرهای native، از نسل ۱ | برای توسعه‌ی کامپایلر در نسل‌های اولیه لازم است. در آینده منسوخ می‌شود. |

- `char*` در کد امن و خارج از `unsafe` خطای کامپایل است.
- تبدیل بین `string` و `char*` فقط داخل `unsafe` مجاز است.

### ۴.۶ خطا و `try` / `catch` / `throw` [پیشنهاد]

- `try`، `catch`، و `throw` پیشنهاد شده‌اند تا مدیریت خطا خوانا باشد.
- نگاشت به C++ با `try`/`catch`/`throw` واقعی انجام می‌شود، با `-fexceptions`.
- **هشدار سرعت:** استثناها روی مسیر اجرای عادی هزینه دارند و با هدف «بدون overhead» تعارض دارند. پس:
  - در نسل‌های ۱ تا ۶ **اضافه نمی‌شوند**. کامپایلر خطاها را با مقدار بازگشتی یا کد خروج مدیریت می‌کند.
  - از نسل ۷ به بعد، **اختیاری** هستند و با فلگ target فعال می‌شوند (`exceptions = on`).
  - در کد امن، `throw` نشده را باید کاربر `catch` کند یا به بالا منتقل کند؛ کامپایلر بررسی می‌کند. [پیشنهاد]

### ۴.۷ `nullptr` [قطعی]

- `nullptr` در کد امن وجود ندارد.
- فقط در `unsafe` و هدرهای native قابل استفاده است.
- برای مقدار «نبودن» در کد امن، در نسل‌های بعد یک نوع امن (مثل `Option<T>`) اضافه می‌شود. [باز]

### ۴.۸ آرایه و بررسی اندیس [باز]

- آرایه‌ی ثابت `T[N]` از نسل ۴.
- بررسی اندیس خارج از محدوده: پیشنهاد این است که **فعال** باشد. هزینه‌ی کوچکی دارد و خطای حافظه را حذف می‌کند. گزینه‌ی غیرفعال‌سازی با فلگ target در دسترس است.

### ۴.۹ متغیر بدون مقدار و استفاده از مقدار بعد از انتقال [پیشنهاد]

- هر `let` باید مقدار اولیه داشته باشد.
- بعد از انتقال مالکیت (در نسل‌های بعد)، استفاده از مقدار خطای کامپایل است.

### ۴.۱۰ سرریز عدد صحیح [باز]

سرریز علامت‌دار در C++ رفتار تعریف‌نشده است. این مشکل حافظه نیست، ولی بر ایمنی اثر دارد. گزینه‌ها در بخش ۲۳ آمده‌اند.

## ۵. نسل‌ها و زنجیره‌ی bootstrap

### ۵.۱ نمادها [قطعی]

- **`gen_n`**: باینری کامپایلر نسل n.
- **`C_n`**: همان `gen_n` وقتی به‌عنوان کامپایلر استفاده می‌شود (هم‌معنا با `gen_n`).
- **`L_n`**: مجموعه‌ی زبانی که `gen_n` می‌فهمد.
- **`S_n`**: سورس کامپایلر نسل n، که به زبان `L_{n-1}` نوشته شده است.

### ۵.۲ فرمول اصلی [قطعی]

$$
\boxed{\;gen_{n} \;=\; C_{\,n-1}\big(S_{n}\big), \qquad S_{n} \in L_{n-1}\;}
$$

یعنی: **باینری نسل n را کامپایلر نسل n-1 می‌سازد، و سورس آن (`S_n`) باید فقط با قابلیت‌های `L_{n-1}` نوشته شده باشد.**

### ۵.۳ قواعد [قطعی]

1. **`S_n ∈ L_{n-1}`**: سورس نسل n فقط از قابلیت‌های نسل قبل استفاده می‌کند، چون نسل قبل باید آن را کامپایل کند.
2. **`L_{n-1} ⊆ L_n`**: زبان هر نسل، زیرمجموعه‌ی نسل بعد است. حذف قابلیت فقط با یادداشت مهاجرت مجاز است.
3. **`gen_n` زبان `L_n` را پیاده‌سازی می‌کند**، یعنی قابلیت‌های جدید همان نسل را هم می‌فهمد.
4. **خودکامپایلی از نسل بعد شروع می‌شود**: `gen_n` وقتی می‌تواند `S_{n+1}` را کامپایل کند که `S_{n+1} ∈ L_n` باشد؛ یعنی `gen_n` تا وقتی `L_n` را کامل پیاده نکرده، نمی‌تواند سورس خودش را (که در `L_n` نوشته شده) کامپایل کند.
5. **شرط نقطه‌ی ثابت**: برای هر `k`، اگر `S_k ∈ L_k` باشد، خروجی C++ بایت‌به‌بایت یکسان است:

$$
C_k\big(S_k\big) \;=\; C_{k+1}\big(S_k\big)
$$

6. **نسل قدیمی حذف نمی‌شود، منجمد می‌شود.** `gen_0` (seed فعلی در JavaScript و `compiler.raz` فعلی) فقط برای ساخت `gen_1` به کار می‌رود. [قطعی]

### ۵.۴ زنجیره

```
gen_0 (seed JS)
   │  gen_1 = C_0(S_1),    S_1 ∈ L_0
   ▼
gen_1
   │  gen_2 = C_1(S_2),    S_2 ∈ L_1
   ▼
gen_2
   │  gen_3 = C_2(S_3),    S_3 ∈ L_2
   ▼
  ...
```

### ۵.۵ تقسیم قابلیت‌ها بین نسل‌ها [پیشنهاد]

| نسل | زبان `L_n` (قابلیت‌های جدید) | دلیل ترتیب |
|---|---|---|
| `gen_1` (`raz-1.0`) | top-level بدون `main`، `function` با `->`، `let`، `if`/`while`/`return`، `include`، `use`، `i64`، `string`، `void`، `unsafe` با `char*`، آرگومان‌های CLI از طریق `argc`/`argAt` | حداقل زبانی که کامپایلر خودش را می‌تواند بنویسد |
| `gen_2` (`raz-1.1`) | `const`، `static` (داخل تابع)، `namespace` | سازمان‌دهی کد کامپایلر |
| `gen_3` (`raz-1.2`) | انواع C (`i8`..`u64`، `f32`، `f64`، `bool`، `char`)، تبدیل صریح `(T)x` | تایپ‌های نزدیک به سخت‌افزار |
| `gen_4` (`raz-1.3`) | `struct`، آرایه‌ی ثابت `T[N]`، اشاره‌گر `T*` و `nullptr` (فقط در `unsafe`) | ساختار داده |
| `gen_5` (`raz-1.4`) | `for`، `break`، `continue`، `++`، `--`، `+=` و عملگرهای مرکب | کنترل جریان کامل |
| `gen_6` (`raz-1.5`) | بررسی اندیس آرایه، `Option<T>` ساده، بهبود پیام خطا | ایمنی |
| `gen_7` (`raz-1.6`) | `try` / `catch` / `throw` (اختیاری با فلگ target) | مدیریت خطا |
| `gen_8` به بعد | `Box<T>` (heap امن)، بررسی مالکیت و انتقال (move)، حذف `char*` از کد امن | ایمنی کامل |

> **چرا `char*` در `gen_1` است؟** چون `S_2` (سورس `gen_2`) باید بتواند رشته‌های C را برای CLI و نوشتن فایل خروجی بخواند. اگر `char*` در `gen_1` نباشد، `S_2` نمی‌تواند نوشته شود. این `char*` فقط داخل `unsafe` است.

## ۶. راهنمای توسعه‌دهندگان: فرمول نسل‌ها با مثال

این بخش برای توسعه‌دهندگان جدید است. هدف این است که بتوانند یک قابلیت را به زبان اضافه کنند بدون اینکه زنجیره را بشکنند.

### ۶.۱ قاعده‌ی طلایی

> **سورس یک نسل را هرگز با قابلیتی که خودِ همان نسل اضافه می‌کند ننویسید.** آن قابلیت را فقط در نسل بعد از آن استفاده کنید.

### ۶.۲ مثال: اضافه کردن `for` در `gen_5`

فرض کنید `gen_4` (`L_4`) حلقه‌ی `while` را دارد ولی `for` ندارد. می‌خواهیم `for` را در `gen_5` اضافه کنیم.

**گام ۱: نوشتن `S_5` با `L_4`.** در سورس کامپایلر، پارسر و بک‌اند `for` را پیاده می‌کنیم، ولی **خود کد `S_5` از `for` استفاده نمی‌کند.** به‌جای آن از `while` استفاده می‌کنیم.

```raz
// داخل S_5 (کد کامپایلر)، ممنوع:
for (let i: i64 = 0; i < n; i++) { ... }

// مجاز:
let i: i64 = 0;
while (i < n) {
    ...
    i = i + 1;
}
```

**گام ۲: ساخت `gen_5` با `gen_4`.**

```sh
./gen_4 S_5.raz -o gen5.cpp
c++ -std=c++17 -O2 gen5.cpp -o gen_5
```

یعنی: `gen_5 = C_4(S_5)`.

**گام ۳: ساخت `gen_6` با `gen_5`.** حالا `gen_5` می‌فهمد `for` چیست، پس `S_6` می‌تواند از آن استفاده کند.

```sh
./gen_5 S_6.raz -o gen6.cpp
c++ -std=c++17 -O2 gen6.cpp -o gen_6
```

یعنی: `gen_6 = C_5(S_6)`، که در آن `S_6 ∈ L_5`.

**گام ۴: بررسی نقطه‌ی ثابت برای `k = 5`.** `S_5` را با `gen_5` و با `gen_6` کامپایل کنید؛ باید خروجی یکسان باشد.

```sh
./gen_5 S_5.raz -o A.cpp
./gen_6 S_5.raz -o B.cpp
diff A.cpp B.cpp      # باید خروجی خالی باشد
```

اگر `diff` تفاوت داشت، یعنی `gen_5` یا `gen_6` رفتار متفاوتی دارند و باید باگ را پیدا کرد.

### ۶.۳ اشتباهات رایج

| اشتباه | نتیجه | راه‌حل |
|---|---|---|
| استفاده از `for` در `S_5` | `gen_4` خطا می‌دهد: `E0001` | در `S_5` از `while` استفاده کنید |
| تغییر `gen_4` بعد از ساخت `gen_5` | زنجیره‌ی قبلی دیگر قابل بازتولید نیست | `gen_4` را منجمد کنید؛ تغییرات را در `gen_5` بیاورید |
| `diff` ناقص بین `A.cpp` و `B.cpp` | نقطه‌ی ثابت نقض شده | بررسی نام‌های تولیدشده و ترتیب توابع |
| قابلیتی در `L_n` اضافه شده ولی در تست‌ها نیست | نسل بعد ممکن است آن را اشتباه تفسیر کند | هر قابلیت باید تست مثبت و منفی داشته باشد (بخش ۲۱) |

### ۶.۴ مثال شروع زنجیره: `gen_0` → `gen_1`

`S_1` باید به `L_0` نوشته شود. یعنی باید از `function main() -> i64` استفاده کند، چون `gen_0` این شکل را می‌فهمد و `main` اجباری دارد.

```raz
// S_1.raz  (زبان L_0 - نسل قدیم)
function main() -> i64 {
    // کد کامپایلر نسل ۱
    return 0;
}
```

پس از ساخت `gen_1`، نسل ۱ دیگر `main` نمی‌خواهد. `S_2` به `L_1` نوشته می‌شود و بدون `main` است:

```raz
// S_2.raz  (زبان L_1 - بدون main)
let inputPath: string = argAt(1);   // ورودی CLI از بخش ۱۷
// کد کامپایلر نسل ۲
```

### ۶.۵ نسخه‌گذاری باینری‌ها [پیشنهاد]

- هر باینری با شماره‌ی نسل نام‌گذاری شود: `razc-1`، `razc-2`، و...
- هر باینری یک فایل `.sha256` همراه دارد.
- نسل منجمدشده (`gen_0`) و هر نسل که نقطه‌ی ثابت آن تأیید شده، در `seeds/` نگه‌داری می‌شود.

## ۷. مدل کلی کامپایل (Pipeline)

```
فایل اصلی (.raz)
  │
  ├─ 1. Lexer            : تبدیل متن به توکن
  ├─ 2. Include expander : الحاق متنی include ها (بخش ۱۴)
  ├─ 3. Parser           : ساخت AST
  ├─ 4. Use collector    : جمع‌آوری use ها و انتقال به بالا (بخش ۱۵)
  ├─ 5. Name resolution  : حل نام‌ها، namespace، globals (بخش ۱۶)
  ├─ 6. Type checker     : بررسی تایپ‌ها
  ├─ 7. Safety checker   : بررسی unsafe، اشاره‌گر، مقدار اولیه (بخش ۴)
  ├─ 8. RIR              : نمایش میانی مستقل از مقصد
  ├─ 9. RIR verifier     : بررسی سلامت RIR
  ├─ 10. Backend C++17   : تولید کد C++
  └─ 11. c++ (GNU)       : کامپایل نهایی به باینری
```

هر مرحله ورودی و خروجی مشخص و تست‌پذیر دارد. [پیشنهاد]

## ۸. فایل اصلی، مدل اجرا و متغیرهای سطح فایل

### ۸.۱ بدون نقطه‌ی ورود [قطعی]

کاربر تابع `main` نمی‌نویسد. کامپایلر کل فایل اصلی را به بدنه‌ی یک `main` در C++ تبدیل می‌کند.

### ۸.۲ قواعد تولید خروجی [پیشنهاد]

1. **دستورهای سطح فایل** به ترتیب در بدنه‌ی `main` می‌آیند.
2. **اعلان‌های تابع و struct و namespace** در فضای فایل خروجی، قبل از `main` قرار می‌گیرند.
3. **prototype خودکار** برای هر تابع تولید می‌شود، پس ترتیب تعریف مهم نیست.
4. **`use`** ها به بالای خروجی منتقل می‌شوند.
5. **`return 0;`** ضمنی در پایان `main` اضافه می‌شود.
6. **`return` در سطح فایل** مجاز است و کد خروج را تعیین می‌کند.

### ۸.۳ متغیرهای سطح فایل (global) [پیشنهاد]

- `let` در سطح فایل یک **متغیر global** است.
- **اعلان** آن در فضای فایل خروجی قبل از `main` قرار می‌گیرد، تا توابع بتوانند به آن دسترسی داشته باشند.
- **مقداردهی اولیه** (`= e`) در همان جایی انجام می‌شود که در فایل نوشته شده، یعنی داخل `main` به ترتیب.
- قبل از مقداردهی، متغیر global مقدار صفر یا پیش‌فرض تایپ را دارد (مثل C++ برای static storage).
- استفاده از یک global قبل از تعریفش در فایل، خطای کامپایل است.

```raz
use linux;
let count: i64 = 0;                 // اعلان global؛ مقداردهی داخل main

function bump() -> void {
    count = count + 1;              // مجاز: global در تابع
}

bump();
echo("count is set");
```

خروجی C++ (شماتیک):

```cpp
#include <linux/...>
std::int64_t count;                 // اعلان در فضای فایل
void bump(void) { count = count + 1; }

int main(void) {
    count = 0;                      // مقداردهی در محل نوشته‌شده
    bump();
    echo("count is set");
    return 0;
}
```

### ۸.۴ `const` سطح فایل [پیشنهاد]

- `const` سطح فایل مقدار ثابت دارد و مقداردهی آن باید **ثابت زمان کامپایل** باشد. این کار مقداردهی زودهنگام را حذف می‌کند.

### ۹.۱ کامنت [پیشنهاد]

- تک‌خطی: `// ...`
- چندخطی: `/* ... */`

### ۹.۲ شناسه‌ها [پیشنهاد]

- شروع با حرف یا `_`، ادامه با حرف، رقم یا `_`.
- حساس به حروف بزرگ و کوچک.
- حروف ASCII.

### ۹.۳ کلیدواژه‌ها [قطعی برای نسل ۱]

کلیدواژه‌های نسل‌های بعد: `for`، `break`، `continue` (نسل ۵)، `try`، `catch`، `throw` (نسل ۷)، و انواع C (`i8`..`u64`، `f32`، `f64`، `bool`) در نسل ۳.

> `char` در فهرست بالا به‌عنوان نوع کاراکتر است؛ `char*` که اشاره‌گر است فقط داخل `unsafe` مجاز است.

### ۹.۴ literal ها [پیشنهاد]

| تهی | `nullptr` | فقط داخل `unsafe` |

### ۹.۵ `;` و بلوک [قطعی]

- هر دستور و هر اعلان با `;` پایان می‌یابد.
- بلوک `{ }` بعد از `}` نیاز به `;` ندارد، مگر در مقداردهی با بلوک (مثل `let s: Point = {1, 2};`).

## ۱۰. تایپ‌ها

### ۱۰.۱ تایپ‌های نسل ۱ [قطعی]

| تایپ | معنی | نگاشت C++ |
|---|---|---|
| `i64` | عدد صحیح ۶۴ بیتی با علامت | `std::int64_t` |
| `void` | بدون مقدار (فقط بازگشت تابع) | `void` |
| `string` | رشته‌ی مالک حافظه (امن) | `std::string` |
| `char*` | اشاره‌گر به کاراکتر (فقط `unsafe`) | `char*` |

### ۱۰.۲ تایپ‌های نسل ۳ [پیشنهاد]

| تایپ | نگاشت C++ |
|---|---|
| `i8`، `i16`، `i32`، `i64` | `std::int8_t` تا `std::int64_t` |
| `u8`، `u16`، `u32`، `u64` | `std::uint8_t` تا `std::uint64_t` |
| `f32`، `f64` | `float`، `double` |
| `bool` | `bool` |
| `char` | `char` |

### ۱۰.۳ اشاره‌گر و آرایه [پیشنهاد]

- اشاره‌گر `T*` (نسل ۴): فقط در `unsafe`.
- آرایه‌ی ثابت `T[N]` (نسل ۴): در کد امن، با بررسی اندیس (بخش ۴.۸).

### ۱۰.۴ نام تایپ‌ها و تغییر آینده [قطعی]

نام تایپ‌ها فعلاً مانند `i64` هستند. در صورت تغییر به نام‌های دیگر، فقط جدول alias تغییر می‌کند.

### ۱۰.۵ تبدیل تایپ [پیشنهاد]

- تبدیل ضمنی فقط در جهت گسترش (widening) مجاز است؛ مثلاً `i32` به `i64`.
- تبدیل کاهشی و بین علامت‌دار و بی‌علامت باید صریح باشد: `(i32)x`.

### ۱۰.۶ تایپ‌های حذف‌شده [قطعی]

`List<T>`، `Ref<T>`، و هر generic تعریف‌شده توسط کاربر حذف می‌شوند. (`List` در `gen_0` وجود دارد و فقط برای کامپایل `S_1` استفاده می‌شود.)

## ۱۱. اعلان‌ها

### ۱۱.۱ `let` [قطعی]

```raz
let p: i64 = 10;
p = p + 1;                 // مجاز: let تغییرپذیر است
```

- تایپ صریح الزامی است.
- مقدار اولیه الزامی است. [پیشنهاد]
- `let` تغییرپذیر است.

### ۱۱.۲ `const` [پیشنهاد]

```raz
const LIMIT: i64 = 100;
LIMIT = 5;                 // خطای کامپایل
```

- تغییرناپذیر است. نگاشت به `const T x = e;` در C++.
- در سطح فایل باید مقدار زمان کامپایل داشته باشد (بخش ۸.۴).

### ۱۱.۳ `static` [پیشنهاد، نسل ۲]

- `static` داخل تابع یا بلوک: نگاشت به `static` در C++ (ماندگار بین فراخوانی‌ها).
- `static` در سطح فایل: خطای کامپایل. متغیرهای سطح فایل همیشه global هستند.

### ۱۱.۴ تابع [قطعی برای امضا]

```raz
function name(p1: T1, p2: T2) -> R {
    // بدنه
}
```

- برای تابعی که چیزی برنمی‌گرداند: `-> void`.
- نام و تایپ همه‌ی پارامترها الزامی است.
- پارامترها کپی می‌شوند (بخش ۴.۴).
- سینتکس C (`i64 name(i64 p)`) در نسل‌های بعد اضافه می‌شود. [باز]

### ۱۱.۵ `struct` [قطعی، نسل ۴]

```raz
struct Point {
    x: i64;
    y: i64;
}

let p: Point = {1, 2};
p.x = 10;
```

- فیلدها با `;` پایان می‌یابند.
- مقداردهی با `{...}` مانند C.
- `new` وجود ندارد. struct کپی می‌شود.
- نگاشت به `struct` در C++.

### ۱۱.۶ `namespace` [پیشنهاد، نسل ۲]

```raz
namespace math {
    function square(x: i64) -> i64 {
        return x * x;
    }
}

let y: i64 = math::square(4);
```

- نگاشت مستقیم به `namespace` در C++.
- نسل ۲: فقط یک سطح تودرتو.

## ۱۴. `include` (الحاق متنی)

### ۱۴.۱ تعریف [قطعی]

```raz
include "lib/math.raz";
```

- کل فایل به‌صورت متنی جایگزین این دستور می‌شود، در همان محل و همان خط.
- کل فایل وارد می‌شود، بدون انتخاب تابع یا متغیر خاص.
- همه‌ی اعلان‌های آن public هستند.

### ۱۴.۲ مکان مجاز [قطعی]

`include` در هر جایی که دستور مجاز است: سطح فایل، داخل `if`، انتهای فایل.

### ۱۴.۳ قانون محتوا [پیشنهاد]

- **اعلان‌ها** (`function`، `struct`، `namespace`، `use`، `let` سطح فایل) فقط در **سطح فایل** مجازند. اگر `include` داخل تابع یا بلوک باشد و محتوایش اعلان داشته باشد، خطای `E0008` است.
- **دستورهای اجرایی** (`if`، `while`، فراخوانی تابع، `let` داخل بلوک) در هر جایی مجازند.

> مثال: `lib.raz` فقط تابع دارد و داخل `if` include شود، خطا می‌دهد. اگر فقط دستور اجرایی دارد، داخل `if` قابل قبول است.

### ۱۴.۴ تکرار و چرخه [پیشنهاد]

- **چرخه** (A → B → A): خطای `E0007`.
- **تکرار غیرچرخه‌ای** (A و B هر دو C را include کنند): C یک بار الحاق می‌شود و بار دوم با هشدار نادیده گرفته می‌شود.
- شناسه‌ی فایل مسیر کانونیک آن است.

### ۱۴.۵ مسیر [پیشنهاد]

- مسیر نسبی به فایلی که `include` در آن نوشته شده نسبت داده می‌شود.
- مسیر مطلق مجاز است.

### ۱۴.۶ شکل دستور [باز]

`include "x";` (پیشنهاد، بدون پرانتز) یا `include("x");`.

## ۱۵. `use` (هدرهای خارجی)

### ۱۵.۱ دو شکل [قطعی]

```raz
use linux;               // هدر استاندارد خود زبان (از جدول target)
use "some_header.hpp";   // هدر واقعی C/C++ از مسیر داده‌شده
```

- `use name;` (بدون نقل قول): هدر استاندارد زبان که در جدول target تعریف شده. نام ناشناخته خطای `E0006` است.
- `use "path";` (با نقل قول): مستقیم به `#include "path"` تبدیل می‌شود.

### ۱۵.۲ مکان [قطعی]

`use` در هر فایلی (اصلی یا include‌شده) و هر جایی قابل نوشتن است. کامپایلر همه را جمع می‌کند و به بالای خروجی می‌برد.

### ۱۵.۳ تکراری‌ها [قطعی]

`use` های تکراری فعلاً حذف نمی‌شوند. حذف تکراری‌ها در نسل بعد اضافه می‌شود.

### ۱۵.۴ هدرهای native و `unsafe` [پیشنهاد]

- هدرهایی که با `use "..."` وارد می‌شوند می‌توانند اشاره‌گر داشته باشند، ولی کاربر فقط داخل `unsafe` از آن‌ها استفاده کند. اگر هدر توابعی با اشاره‌گر برگرداند، کامپایلر مقدار را فقط داخل `unsafe` می‌پذیرد. [پیشنهاد]
- این یعنی زبان امکان استفاده از C++ را دارد، ولی ایمنی حفظ می‌شود.

## ۱۶. namespace، globals و حل نام

- نام‌ها در فضای فایل و namespace تعریف می‌شوند.
- دسترسی با `::`.
- تداخل نام در فضای فایل خطای `E0005` است.
- چون همه‌ی فایل‌ها الحاق می‌شوند، namespace برای جلوگیری از تداخل در کتابخانه‌ها لازم است. [پیشنهاد]
- متغیرهای global (بخش ۸.۳) در حل نام همان فضای فایل هستند.

## ۱۷. Runtime، FFI و argv

### ۱۷.۱ مرز کامپایلر و runtime [قطعی]

- کامپایلر توابع کتابخانه‌ای (مثل `echo`) را نمی‌شناسد.
- توابع کتابخانه‌ای در هدر C++ هستند و با `use "..."` وارد می‌شوند.
- جدول `builtins` در `config/language.json` در نسل جدید حذف می‌شود. [پیشنهاد]

### ۱۷.۲ `main` و argv [قطعی]

- زبان `main` ندارد. اما کامپایلر برای گرفتن ورودی CLI (مثل مسیر فایل) به `argc` و `argv` نیاز دارد.
- در بک‌اند، برای target از نوع `cli`، تابع `main` تولیدشده به شکل `int main(int argc, char** argv)` است. این یک **جزئیات تولید کد** است، نه یک تابع که کاربر بنویسد.
- هدر bridge (`raz_cli.hpp`) مقدارهای `argc` و `argv` را به **متغیرهای global امن** کپی می‌کند تا کد Raz بدون اشاره‌گر به آن‌ها دسترسی داشته باشد.

### ۱۷.۳ شکل متغیرهای argv [باز]

دو گزینه:

- **الف)** متغیر global `argc: i64` و تابع `argAt(i: i64) -> string`. این گزینه generic ندارد و با حذف `List` سازگار است. **پیشنهاد نویسنده.**
- **ب)** متغیر global `args: List<string>`. این گزینه ساده‌تر است ولی `List` را برمی‌گرداند که با حذف generic در تعارض است.

نمونه‌ی گزینه‌ی (الف) در کد کامپایلر:

```raz
use "raz_cli.hpp";
let argc: i64 = argCount();          // global
let input: string = argAt(1);        // global پس از مقداردهی
```

### ۱۷.۴ FFI [قطعی]

چون Raz به C++ تبدیل می‌شود، هر هدر C++ که `use` شود قابل استفاده است. هیچ wrapper یا overhead اضافه‌ای نیست. امن بودن این هدرها با بخش ۱۵.۴ کنترل می‌شود.

## ۱۸. نگاشت کلی به C++17

| سازه‌ی Raz | خروجی C++17 |
|---|---|
| دستورهای سطح فایل | بدنه‌ی `int main(void)` (یا `(int argc, char** argv)` در حالت CLI) |
| `function f(...) -> R { }` | `R f(...) { }` + prototype |
| `let x: T = e;` (سطح فایل) | اعلان global + مقداردهی در `main` |
| `let x: T = e;` (داخل بلوک) | `T x = e;` |
| `const x: T = e;` | `const T x = e;` |
| `static x: T` داخل تابع | `static T x` |
| `struct S { ... }` | `struct S { ... };` |
| `namespace n { ... }` | `namespace n { ... }` |
| `use name;` | `#include <name>` (از جدول target) |
| `use "f";` | `#include "f"` |
| `include "f";` | الحاق متنی قبل از تولید |
| `string` | `std::string` (مالک حافظه، RAII) |
| `char*` | `char*` (فقط `unsafe`) |
| `make` برای heap (نسل ۸) | `std::make_unique<T>(...)` |
| `auto` در کد تولیدشده | استنتاج تایپ برای متغیرهای داخلی کامپایلر؛ کاربر تایپ صریح می‌نویسد |
| `try`/`catch`/`throw` (نسل ۷) | `try`/`catch`/`throw` با `-fexceptions` |
| `nullptr` | `nullptr` (فقط `unsafe`) |
| `i64` | `std::int64_t` |
| `void` | `void` |

## ۲۰. ساخت و target

### ۲۰.۱ زنجیره [قطعی]

```
raz → (کامپایلر) → C++17 → (g++/gcc با -O2) → باینری
```

### ۲۰.۲ فایل target [پیشنهاد]

`config/targets/cpp17.json` شامل:

- کامپایلر C++ (`c++`، `g++`)،
- فلگ‌ها (`-std=c++17 -O2`)،
- جدول `use` های استاندارد (مثلاً `linux` → مسیر هدر)،
- نوع entry (`cli` یا `none`)،
- فلگ `exceptions` (از نسل ۷)،
- فلگ `bounds_check` (از نسل ۶).

### ۲۰.۳ بدون overhead [قطعی]

- هیچ runtime خودکار تولید نمی‌شود.
- هیچ GC یا بررسی پنهان نداریم، مگر بررسی‌هایی که با فلگ فعال شده‌اند.

---

## ۲۱. تست‌ها [پیشنهاد]

- هر قابلیت یک تست **مثبت** و یک تست **منفی** دارد.
- تست منفی کد خطای مورد انتظار را بررسی می‌کند.
- تست‌های نسل‌های قبل باید سبز بمانند (تست رگرسیون).
- هر نسل تست **نقطه‌ی ثابت** (بخش ۵.۳ بند ۵) را اجرا می‌کند.
- تست‌های امنیتی: کامپایل برنامه‌ای که اشاره‌گر را خارج از `unsafe` استفاده می‌کند باید `E0009` بدهد.

## ۲۴. مراحل بعدی

1. تأیید موارد باز بخش ۲۳ (به‌ویژه ۱، ۳، ۵، ۸).
2. تأیید تقسیم قابلیت‌ها بین نسل‌ها (بخش ۵.۵).
3. نوشتن `S_1` به زبان `L_0` (شامل `function main`، بدون قابلیت‌های نسل ۱).
4. کامپایل `S_1` با `gen_0` و ساخت `gen_1`.
5. نوشتن تست‌های `gen_1` (مثبت، منفی، و `E0009`).
6. اجرای تست نقطه‌ی ثابت برای `k = 1`، سپس نوشتن `S_2` به `L_1`.
